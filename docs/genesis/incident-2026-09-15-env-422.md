## The refused key: `NETLIFY_AUTH_TOKEN`

Read live off the site (`c063340c-4def-44e3-a553-de7754b2437f`), the only two site-level env vars
that exist are, in write order:

| key | written | scopes | contexts | secret |
|---|---|---|---|---|
| `NETLIFY_BUILD_HOOK_URL` | 12:14:19Z | `functions` | `production` | yes |
| `TRACKING_PROJECT_ID` | 12:14:20Z | `builds, functions, post_processing, runtime` | `all` | no |

Nothing after. The account level (`GET /accounts/{id}/env`, no `site_id`) holds only
`TRACKING_SINK_URL` and `TRACKING_SINK_TOKEN`, both `context: all`, `is_secret: false` — the two keys
genesis deliberately *inherits* and never copies (C-11).

`siteGenesis.ts` writes env vars in exactly this order:

1. `NETLIFY_BUILD_HOOK_URL` — explicit `scopes: ["functions"]`, `context: "production"`, secret ✅
2. `TRACKING_PROJECT_ID` — default scopes, non-secret ✅
3. **the fleet loop** — `for (const fleetVar of genesisFleetEnv.provisioned) setEnvVar(..., { isSecret: fleetVar.isSecret })`
4. the object-store set (`PUBLISH_SECRET`, `ARTIFACT_UPLOAD_TOKEN_SECRET`, `TRACKING_SALT`, `NETLIFY_SITE_ID`)
5. `CMS_AGENT_MCP_ENDPOINT` / `CMS_AGENT_MCP_TOKEN`
6. `ADMIN_EMAILS`, `ROLE_EMAILS_ADMIN`, `ARTIFACT_URL_INGEST_ALLOWED_HOSTS`, `PDF_TOOL_STORAGE_SITE_ID`
7. `MCP_HTTP_AUTH_TOKEN`

Step 3 is the next write after `TRACKING_PROJECT_ID`. `GENESIS_FLEET_ENV_VARS` has exactly one
non-inherited member — `NETLIFY_AUTH_TOKEN`, `isSecret: true` — and the deployment holds its value, so
the loop ran with one iteration.

### The payload, and why Netlify refused it

```jsonc
POST https://api.netlify.com/api/v1/accounts/6917763e9afbf6f211be929b/env?site_id=c063340c-…
[
  {
    "key": "NETLIFY_AUTH_TOKEN",
    "scopes": ["builds", "functions", "runtime", "post_processing"],   // ← NETLIFY_DEFAULT_ENV_SCOPES
    "values": [
      { "value": "…", "context": "production" },
      { "value": "…", "context": "deploy-preview" },
      { "value": "…", "context": "branch-deploy" }
    ],
    "is_secret": true
  }
]
```

Netlify's Secrets Controller documentation:

> Environment variable secrets cannot have the `post processing` [scope] to avoid inadvertently
> exposing the value through features like snippet injection.

`NETLIFY_AUTH_TOKEN` is the **only** secret in this file written without an explicit `scopes`
argument, so it is the only one that inherited `NETLIFY_DEFAULT_ENV_SCOPES` — which contains
`post_processing`. Every other secret passes `scopes: ["functions"]`.

### Why it survived until now

`setEnvVar` already encodes the sibling *context* constraint ("a secret written with context `all`
is refused, because `all` includes `dev`"), learned live and commented in full. The *scope*
constraint was never encountered, because:

- the checkout-backed path delegates provisioning to `create-site.mjs`, which writes its own env set;
- `kugel-genesis-lab-2`, `kugel-fernwell` and `kugel-platform` were all minted with a platform
  checkout mounted, or by hand;
- genesis-lab-3 is the **first live mint on the checkout-less path**, which is the only path that
  reaches this driver's own fleet loop.

### Ruled out

- **A key derived from the hyphenated slug** (`NETLIFY_BUILD_HOOK_URL__GENESIS-LAB-3`, the platform
  #758 family): genesis writes no slug-derived env keys at all. Every key it writes is a literal
  matching `^[A-Z_][A-Z0-9_]*$`. The remedy classifier now names this cause anyway, since it is the
  cheapest 422 to mis-read.
- **A POST for a key that already exists**: the 422 came from the collection `POST`, which
  `setEnvVar` only issues after a `GET .../env/{key}?site_id=…` returned 404. Confirmed by the live
  env list: `NETLIFY_AUTH_TOKEN` does not exist at either level.
- **An empty value**: `resolveGenesisFleetEnvVars` only lists a key as `provisioned` when
  `env[key]?.trim()` is non-empty, and `hook.url` is derived from the hook id when Netlify omits it.

## What was actually wrong — four defects, not one

1. **A2.1 — the write was illegal.** A secret carried `post_processing`. `setEnvVar` now sanitizes the
   scope set for secrets (dropping only the forbidden member, keeping `builds` — the scope T21.8
   exists to protect) and records the drop on the ledger by name.
2. **A2.2 — one refused key ended the mint.** Nine steps that would have succeeded never ran, and the
   registry record — written last — never existed, so the tenant was invisible *and* unrepairable
   (`createProject` refuses `project_exists`, so even a re-run of a half-written mint would fail).
   The record is now written as soon as the site has an id, with `status: "provisioning"`; every
   Netlify write is non-fatal and records a `blockage`; a re-run adopts what exists.
3. **A2.3 — two genesis paths named one tenant two ways.** Both defaulted to the bare slug and the
   `kugel-` prefix lived in an operator's habit of passing `--netlify-site-name`.
4. **A2.4 — the refusal named nothing.** `redactErrorBody: true` discarded Netlify's body, so the key,
   the cause and the way out were all absent. Finding the key required reading the site's live env
   list and counting. A refusal now carries `{code, step, key, netlifyStatus, netlifyMessage, remedy,
   resumable}` onto the wire.
