# Track C recon — what already exists, and where `editorial_planner` had to attach

_2026-09-14. Written before any code, corrected after it. Every path is the path the built code
actually uses; nothing here is a plan._

## 1. The two planes, and what each one owns

| | `vreich-ui/cms-agent` (engine) | `vreich-ui/platform` (tenants) |
|---|---|---|
| Runs | `WorkflowExecutionRecord` in GCS (`runs/{runId}.json`, index `run-index/{projectId}.json`), CAS on `rev` | — |
| The strategy object | reads it | **owns** the contract |
| The requests inbox | — | `/admin/requests` (`EditorialRequest` + one index blob) |
| Commissioning | **owns** the planner | owns the `commissioning` contract + the visibility |

The division that mattered for this track: the engine can start runs but cannot create a platform
request row; the platform creates request rows but cannot start a run except through the engine.

## 2. `strategy-review` — the fan-out template

- Entry `src/agent/entrypoints/strategyReviewJobMain.ts` → `cliMain` → `runStrategyReviewJob` in
  `strategyReviewJob.ts`.
- Tenants come from `resolveStrategyReviewTenants(projects, {env, partitionFilter})`
  (`strategyReviewJob.ts:174`): `projectRepository.list()`, sorted by `projectId`, keeping
  `status === "active"` projects carrying at least one of `clientSiteBinding` / `objectDialect` /
  `tracking` — which is how internal service projects (monetizer, pdf-tool) are excluded. Every
  exclusion is reported **by name with a reason**.
- The strategy is read by `getEditorialStrategy()` (`projects/genesisEditorialStrategy.ts:261`),
  which calls the tenant's `object_get` through `ProjectMcpAdapter.callReadTool` with a 15s timeout
  and **never throws**: four named degradation modes (`object` / `default` / `fallback` /
  `unavailable`).
- Auth per tenant comes off the project record (`mcpEndpointEnvVar` → env, else `mcpEndpoint`;
  bearer from `tokenEnvVar` or `tokenSecretRef`). The job binds nothing per tenant.
- `--dry-run` (or `STRATEGY_REVIEW_DRY_RUN`) prints one address line per tenant and makes no calls.
- Schedule: `deploy-strategy-review-schedule.sh`, cron `0 5 * * 1`, fired through the Cloud Run Jobs
  v1 `:run` endpoint as `SCHEDULER_SA`.
- Image discipline: `scripts/pin-job-images.sh` pins every job in `deploy/executor-jobs.txt` to the
  **digest** `cms-agent-mcp` currently serves, reconciles the list against the project in **both**
  directions (ABSENT / UNLISTED), and `--check` reports drift without deploying. `SERVICE_GIT_SHA`
  is set only by `scripts/deploy-service.sh`, on the service — **no job carried it before this
  track**.

**Adopted for `editorial-planner`:** tenant selection shape, record-only addressing, the
dry-run-prints-then-exits contract, per-tenant failure isolation, `--max-retries 0`.
**Deliberately stricter:** the opt-in lives in the tenant's governed object (not in any env var),
and the job refuses to run at all on a stale image.

## 3. Starting a run — the path the admin chat actually uses

There is no private starter to avoid; there is a two-call public path, and both planes use it.

Platform `run_workspace_workflow` (`packages/core/server/lib/agent/tools.ts:1449`):

```ts
const requestId = args.request_id ?? (await mintWorkspaceRequestId(ctx, args));
const started = await ctx.cmsAgent.callTool('workflow_start_dry_run', {
  projectId, input: dispatchInput, requestId, workflowId?, budgetUsd?, executionMode?
});
await ctx.requests?.register({ request_id, kind, title, brief_excerpt?, workflow: {run_id, workflow_id, project_id, node_total} });
```

- `workflow.start_dry_run` (`mcp/workspace/tools.ts:1042`) → `startDryRun` (`executor.ts:1043`).
  It only **queues**; nothing dispatches. A follow-up `workflow.run_all` / `run_next_node` is the
  kick, after which the continuation tick carries the run.
- `requestId` is validated by `resolveCallerRequestId` (`tools.ts:363`) against
  `objectDialect.requestIdPattern`. A live (`openai`) run on a pattern project with no id is refused
  `request_id_required`; a non-matching id is `invalid_request_id`. `publishRequestId` is a
  **different** field, validated separately, never substituted.
- `publishing_conductor` inputs ride on `input` → `run.initialInput`: `contentSource` and
  `instructions` are read by `input_triage`; `trafficSource` / `awarenessStage` are read off
  `run.initialInput` directly by `extractPlacementSignals` (`executor.ts:2428`) and validated against
  `aggressionVector.ts`.

**Used verbatim by the planner** (`planner/editorialPlanner.ts` → `startCommissionedRun`):
`startDryRun(...)` then one `runNextNode(...)` kick. The only difference from a human-started run is
the `commissionedBy` stamp.

## 4. Runs, health, and what a run record did not carry

- `workflow.list_runs` → `listRunsPage` → `summarizeRunForList` (`executor.ts:167`) — the compact
  row; **no** `initialInput`, by PR #105's compaction contract.
- `workflow.get_run` → compact or `detail:"full"`; `workflow.get_run_cost` → `summarizeRunCost` +
  `plan.nodeTimingAggregates` (EMA/p50/p95 per node).
- `driverHealth` (`workspace/driverHealth.ts`) feeds the `stall` block; it is about drivers, not cost.
- **`commissionedBy` did not exist anywhere** (grep: zero hits), and a run record has no generic
  metadata bag. So the field was added to `WorkflowExecutionRecord`, stamped in `buildInitialRun` at
  birth, and surfaced on the **list row** — the platform's sweep reads it one page at a time rather
  than opening every run.
- Per-run cost for the daily budget comes from the **usage ledger** (`usageRepository.list({projectId,
  from})`), one call for the whole window, rather than `get_run_cost` per run.

## 5. MCP surface

- Every workspace tool is a `tool({name, description, zodSchema, inputSchema, execute})` entry in
  `createWorkspaceTools` (`mcp/workspace/tools.ts:718`), plus spreads of sibling
  `createXTools(...)` modules. Dots become underscores on the wire (`canonicalToolName`).
  → `planner.plan` / `planner.commission` / `planner.status` live in a new sibling
  `plannerTools.ts`, spread in beside `createOperationTools()`.
- `READ_TOOL_ALLOWLIST` (`projects/projectMcpAdapter.ts:130`) is the fixed server-side gate.
  `object_list` is in it; **`analytics_top_content` is not**, and the planner does not reach for it —
  widening that allowlist is its own reviewed change.

## 6. The `editorial_strategy` contract (platform)

- Body: `packages/core/schema/bodies/editorial-strategy-v1.ts` (zod; `editorialStrategyShapeSchema`
  split from the refined `editorialStrategyBodySchema`).
- Contract served from `lib/registry/object-contract.ts` — JSON schema **derived** from the zod body;
  rules in the `'editorial_strategy'` case, each `{id, severity: blocks_write|blocks_publish|warns}`.
- Validation: `server/lib/object-validate.ts`, hand-written; `checkEditorialStrategy(body, atPublish)`.
  Statuses are `ReadinessCriterion.status`: `'missing'` = blocker, `'warning'` = warning,
  `'optional'`/`'info'` = neither.
- The warn-when-absent precedent to copy is `strategy_provenance_set`.
- Genesis skeleton: `packages/core/cli/create-site.mjs` (`strategySkeletonBody`), mirrored by
  `scripts/seed-editorial-strategy.mjs` and pinned against it by
  `tests/scripts/seed-editorial-strategy.test.mjs` — **both** had to gain the block.
- Id `strat_<slug>`: prefix table `lib/object-ids-mint.ts:95`, regex `lib/object-ids.ts:29`.
- `set_strategy_fields` is an **open deep-merge** op with no field allowlist, so `commissioning`
  became writable with no patch-grammar change.

## 7. The requests inbox (platform), and the gap this track found

- `EditorialRequest` + `RequestIndexRow` in `server/lib/requests/store.ts`; the row is projected by
  the single `projectIndexRow`. `RequestRowView` in `lib/admin/requests-client.ts`; the detail pane
  renders `requestFacts()` from `lib/admin/request-logic.ts`.
- `blockage.v1`: types and `remedyButtons` in `lib/admin/blockage.ts`, rendered by
  `admin/BlockageCard.tsx` — "the ONE place a remedy becomes a button".
- **The gap:** `createRequest` has exactly one call site, `ctx.requests.register` in
  `server/lib/agent/context.ts:587`, reached only from chat tools. A run the planner starts on the
  engine plane creates no request row, so it would be invisible on the one screen an operator opens.
  `run_workspace_workflow` is an admin-chat agent tool and is **not** on the tenant `/mcp`, so the
  engine cannot call it.
  → Closed by **adoption** in the sweep (`server/lib/requests/adopt-commissioned.ts`): the sweep
  already polls CMS-Agent every pass with the site's own client, so it now also registers rows for
  runs stamped `commissionedBy` that have none. No new MCP verb and **no credential scope change**.

## 8. `objectDialect.requestIdPattern`

Declared per project on the **engine** side (`src/agent/projects/{platform,drLurie,fernwell}/definition.ts`),
enforced in `resolveCallerRequestId`. The platform repo declares and enforces nothing — it only
notes the field's absence in two artifact-key readers. dr-lurie declares
`^req_[a-z0-9_]+_\d{8}_\d{2}$`; the planner mints `req_planner_<topic>_<yyyymmdd>_<nn>` and refuses
its own minted id at plan time if it does not match.

## 9. ADR #326 — node-definition field ownership

`docs/plan/ADR-2026-09-13-node-definition-field-ownership.md`. Content fields (prompt, schemas, tool
grants, model config) are **store**-owned; topology (`id`, `kind`, `dependsOn`, `produces`,
`riskLevel`, `status`) is **code**-owned, and `nodes.ts` is a generated lockfile.

**Consequence for this track:** `editorial_planner` is deliberately **not** a registered workflow
node. It is a *synthetic* node (the `improvement/rubricJudge.ts` idiom) — built in memory, never
persisted — so it adds nothing to the graph, needs no `nodes:update`, and cannot drift between the
planes. It still inherits schema-constrained JSON, validation retries, the per-call budget guard and
usage recording from the ordinary runner registry.

## 10. Testing

- Engine: vitest, `tests/**/*.test.ts`, `npm test`. CI also gates `typecheck`, `test:drift`,
  `test:glossary`, `test:objects`, `test:scope`. Adding an MCP tool **requires** `npm run
  drift:update` (the two-plane manifest) — the suite fails otherwise.
- Platform: `node:test` on pure modules, compiled via `tsconfig.test.json` into `.tmp/ci-test`;
  UI decisions are extracted into `lib/admin/*.ts` precisely so they can be tested this way.
