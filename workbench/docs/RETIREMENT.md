## 1. Summary for Wolf

The old constellation-as-home-screen UI is not in this repository at all — this build is a clean rewrite, so there is nothing here to delete for most of the proposal's "legacy removal" list; the retirement is really about **turning off / redirecting the old deployed surface** once the new one is live, which is outside this repo's reach and needs its own confirmation of where that old surface actually lives. Inside this repo, the situation is simpler and mostly good news: node-picker-as-graph, global client mode, and workflow-scoped-to-client are already gone in the new build — there's no code path to retire. The one finding that matters is a real gap, not a formality: **`constellation_get_metrics`'s cross-run per-node health data (success rate, avg/max latency, retry counts, human-intervention counts, tool-error counts) and `constellation_get_attention`'s config-defect feed (unconfigured client env vars, skill/tool risk conflicts) have no home anywhere in the shipped UI** — I grepped the whole `app/src` tree for the field names those two verbs return and found zero matches outside of an unrelated connection-test field. Everything else the constellation did (structure, relationships, execution edges) is covered by the node rail, the Grid tab, and the Dependencies tab. Recommend: keep both `constellation_get_metrics` and `constellation_get_attention` live and route them into the Library cards and node inspector before calling the constellation retired, per the proposal's own open question. Also worth noting: the command palette (⌘K) and the graph overlay (⌗) that are supposed to replace constellation navigation are still stub toasts ("Phase 4 — WP-42") in the current build — so nothing constellation-shaped should be turned off until WP-42 actually ships.

**Recommendation counts:** Retire now — 3. Retire after X — 3. Keep — 5.

## 4. Ordered removal sequence

Nothing in this repo needs removing (see §1) — the sequence below is written for whoever retires the **old, currently-deployed** constellation UI, once its location is confirmed (§6, Q1). Each step names its own verification.

1. **Confirm the old UI's deployment target and freeze new traffic to it** (point its URL/redirect at the new Conductor Workbench build, or leave both live behind a flag).
   *Verify:* the old URL now serves the new app, or a banner/redirect; no 404s; check server logs for stragglers after 48h.
2. **Retire the old constellation-as-home-screen route** (row 1).
   *Verify:* the new Library screen (`app/src/screens/Library`) is reachable as the default landing screen in a fresh build; Playwright's existing library smoke spec still passes.
3. **Retire the old node-picker-via-graph-click interaction** (row 2).
   *Verify:* every node reachable via `Workbench/Rail.tsx` within the HANDOFF §7 "two-click rule"; spot-check 5 nodes across all three workflows (`input_triage`, `contract_intelligence`, `publish_executor`, plus 2 clone/capture nodes once WP-42's fixes to `workspace_get_graph`'s coverage gap, if any, land).
4. **Retire the old global-client-mode UI element**, if the old deployed app has one (row 3/4).
   *Verify:* `Runs` History filter and `StartRunModal`'s project field are the only remaining places a client/project appears; grep the new app (already done, clean) stays clean on every future PR.
5. **Do NOT retire any old command-palette-adjacent navigation (search bars, quick-jump menus) until WP-42 ships and passes review** (row 7/8).
   *Verify:* ⌘K in the new build opens a real palette (not the current toast), reaches any node/run/workflow/project/setting in ≤3 keystrokes + Enter per HANDOFF §7.1, and the graph overlay (⌗ / "G") renders `workspace_get_graph` read-only. Only then retire the old nav equivalent.
6. **Do NOT retire the old health-visualization surface (if the old UI has one reading `constellation_get_metrics`/`get_attention`) until that data is surfaced in the new UI** (rows 9/10, §3).
   *Verify:* pick one concrete number from a live call — e.g. `publication_controller`'s `approvalsRequested: 11` — and confirm it (or an equivalent operator-legible statement) appears somewhere in the new build (Library card, Registry, or a new node-inspector panel). Until that's true, keep the old surface reachable even if de-emphasized.
7. **Final sweep for duplicate/dead panels** (row 6) — only after 1-6, so the "what's dead" question is asked against a new UI that's actually complete.
   *Verify:* screen-by-screen diff of the old UI's nav against the new IA (Library / Workbench / Runs / Learning / Registry); anything with no obvious new-UI home gets its own Wolf question rather than silent deletion.

## 5. Do-not-retire list

- **The editors' admin-chat surface and its `agt_client_manager` agent.** Confirmed explicitly out of scope everywhere it's mentioned: proposal's "Legacy removal" paragraph ("the admin-chat path for editors remains its own surface, untouched"), the `CMS_Agent` MCP server's own instructions ("Content production and publishing for a site are meant to go through that site's ADMIN CHAT... platform admin-agent-chat → client_manager"), and `app/src/screens/Registry/AgentsTab.tsx`'s explicit copy ("the editors' admin-chat agent — their surface, not this operator console"). This UI reads the agent's registry entry read-only; it does not own or replace the chat surface itself.
- **`constellation_get_metrics` and `constellation_get_attention` (the verbs, not any specific old screen)** — per §3/§4 item 6, keep both live and callable until their data has a confirmed home in the new UI. Retiring the *verb* was never proposed by anyone; the open question is only about the old *screen* that displayed it.
- **`workflow_*` control verbs and the gate panel's `workflow_set_operator_publish_decision`** — these are core to Phase 2 (already built per the `42bd514` commit) and are the mechanism the whole redesign is built around; nothing suggests retiring them and nothing here does.
- **The Keys & auth screen's "presence/source only, never a value" design** (`Registry/KeysTab.tsx`) — this is a safety property (HANDOFF §3: "Secrets: none in the UI, ever"), not a legacy behaviour; do not simplify it toward showing values even for convenience.
- **Per-project tool-policy data (`toolPolicies`) and the `needs_approval` distinction** — proposal's open question #2 ("should tool-level needs_approval policies surface in the gate panel, or stay a registry concern") is explicitly unresolved; until Wolf answers it, keep both the registry rendering (built) and the policy data itself.
