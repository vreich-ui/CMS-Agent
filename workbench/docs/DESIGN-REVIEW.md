# Conductor Workbench — Design & Copy Review (WP-R gate)

Reviewed against `spec/HANDOFF.md` §7 (ten-point UX acceptance checklist), `spec/proposal.html` (six design principles), and `spec/mockup.html` (the visual spec), using the screenshots in `app/shots/` as primary evidence, cross-checked against `app/src` where the screenshots raised a question. Read-only review — no application code changed.

---

## Part 1 — Design critique

**Verdict:** The bones are right — run-centric layout, phase-ordered rail, the gate panel as a first-class object, honest "not captured" labels instead of fake data — and several individual screens (Keys & auth, Start-run modal, the Reset-run confirm dialog, the regression watchboard) are genuinely excellent, publication-quality expert-tool UI. But the console fails its own headline rule (§7.8: amber reserved for attention/gates) systemically, not as an edge case — the same accent color is the default "primary button" everywhere, which means gates don't visually outrank ordinary actions the way the whole design is supposed to guarantee. Combined with a duplicated gate explanation, a "Live" tab where nothing is live, and several places where the tool explains its own design decisions to the operator instead of the data, the console is legible but not yet the "instantly legible, doesn't need explaining" bar Wolf set.

**Score: 7 Pass · 2 Partial · 1 Fail.**

### Visual consistency

- **Type & spacing rhythm** are consistent across screens — same card padding, same label caps-and-tracking style for section eyebrows (`INTAKE`, `RUBRICS · 5 ACTIVE`, `EXECUTION RECORD`), same mono treatment for ids/timestamps. This is the payoff of extracting `tokens.css`/`base.css` verbatim rather than reinventing per-screen.
- **Tabular numbers**: aligned cleanly in `runs-grid-*.png` and `registry-tools.png`; costs and durations in the History table (`runs-history.png`) line up correctly.
- **The single amber accent** is not reserved for attention/gates (see §7.8 above) — this is the one real system-wide consistency failure, and it's the most consequential one because it's load-bearing for the entire "where did this run stop" promise.
- **Secondary decorative-looking amber use**: the horizontal bar under each candidate card in Compare (`learning-compare.png`) has no visible label — it reads as a score/confidence meter but nothing on screen says what it measures, and its color (amber) invites the "this needs attention" read even though nothing there is blocked.

### Hierarchy — "where did this run stop, what do I do?"

- On the workbench's Run mode (`bench-run-light.png`, `gate-panel.png`), the answer is right there twice — almost too well. The **Gate** explanation is printed once as a card in the center "This run" tab and again, nearly verbatim (plus one extra warning line), in the right-hand dock. Two boxes with the same heading ("GATE") and near-identical paragraphs compete for the same reading — an operator's eye has to reconcile them to notice the dock version added the crucial "Approving here is expected to publish live content — not a draft, not a simulation" line. Consolidating to one authoritative gate explanation (the dock's, since it has the extra warning) with a one-line pointer from the center tab would sharpen exactly the hierarchy the product exists to deliver.
- The **Runs → Live** tab is a hierarchy problem by omission: its job (per `LiveTab.tsx:1-4`) is "what needs me right now" — running, paused, *or* blocked. In the reviewed data all 18 cards are `blocked`; zero are actually running. A tab literally labelled "Live" showing no live runs reads, at a glance, as broken or stale rather than as "this is where your attention is needed" — which is exactly backwards from the intent.
- Elsewhere hierarchy is well-judged: the node rail's phase grouping puts execution order ahead of graph position (matching principle 2), and the bound-run chip in the top bar keeps "whose reality am I looking at" answered everywhere.

### Both themes

No theme-specific failures found. The one thing worth double-checking outside static screenshots: the Compare candidate cards' unlabeled amber bar and the rail's fan-in glyph (see Copy review) should be re-eyeballed in dark mode specifically, since low-contrast small glyphs are the class of thing that degrades unevenly between themes.

### Density without noise

- **Where density is right**: the tool registry (`registry-tools.png`), the runs grid, and the node rail pack real information into small type without needing whitespace to breathe — appropriate for a single expert operator.
- **Where density tips into noise**: `learning-compare.png` and `runs-live.png` both float a toast notification and the persistent "fixture data" badge in the same bottom-right corner simultaneously, overlapping each other; `registry-tools.png`'s fixture badge overlaps the `capture.score` row's description text outright. Minor but real — two pieces of chrome fighting for the same 200×80px of screen.
- **Where whitespace fails the operator**: `runs-history.png`, `learning-evaluate.png`, and `bench-build.png` all show a small amount of real content sitting in the top-left of an otherwise empty canvas — half to two-thirds of the viewport is unused. For a "dense expert tool" this reads as under-designed rather than restful; it's the flip side of the density problem, not a contradiction of it.
- **Graph overlay** (`graph-overlay.png`): the DAG is horizontally scrollable (`overflow:auto` in `GraphOverlay.tsx:104`) but the screenshot shows columns cut off at the modal edge with zero visual cue (no fade, no scrollbar, no "→ more") that there's anything past `DRAFTING`. A reader would reasonably conclude the overlay is just clipped.

### Three highest-impact design improvements, ranked

1. **Reserve amber for attention/gates only.** Introduce a neutral primary-button style (ink-filled or ink-bordered, no accent) for ordinary CTAs — Save, Start run, Promote, Sign in, Run regression now — and keep amber exclusively for gate/blocked/needs-approval states. One token change (`base.css:52` plus every `variant="pri"` call site that isn't actually gate-adjacent) fixes the single biggest gap between the stated design principle and the shipped system, and immediately makes a blocked run visually outrank every other screen in the app the way it's supposed to.
2. **Collapse the duplicated gate explanation and rename the "Live" tab to match its contents.** Both are hierarchy fixes in service of the product's one stated job. Keep the dock's fuller gate copy as the single source, replace the center tab's copy with a one-line pointer; rename "Live" to something that's still true when every card is blocked (e.g. "Needs you," or split running/paused from blocked as visually distinct groups within the same tab).
3. **Strip the design-rationale captions from user-facing footers while making the genuine truth-telling captions visually distinct.** ("Airflow's grid view: runs as columns…", "the list API already computes it", "Tool-policy split rendered as a scannable bar, not JSON" — see Part 2 for full list.) These read as commentary left in from the build process, not information for an operator, and right now they sit in the exact same low-contrast footnote style as the "topology is seed-pinned" disclosures that must stay and must be trusted.

## Part 2 — UX copy review

**Verdict:** The confirm-dialog and toast system is the strongest thing in the product — every mutating action goes through one `confirmAction()` wrapper (`src/api/confirmAction.ts`) that names the verb and states the effect in plain language, and the toasts that follow are almost uniformly past-tense and verb-attributed. Truth-telling about live/pinned data is handled with unusual honesty (duration "not captured," compare pairs explicitly "illustrative — no live compare-queue verb exists yet," Monetizer's missing token spelled out as "Monetizer runs will refuse"). Against that strong baseline, three things stand out as real defects, not polish: (1) several user-facing strings hardcode "the mock backend" into copy that will also run live, which will eventually be a lie; (2) a handful of footers describe the app's own design decisions to the reader instead of describing data; (3) the gate panel — the copy the brief says to scrutinize most — is precise everywhere except in the one place operators will read fastest, the Live-card summary line, which flattens every gate into "the operator publish decision" regardless of what's actually being approved.

### What already works well (worth preserving, not just noting)

- `confirm-dialog.png` — "Reset run / `workflow_reset_run` / Reset run run_…back to queued, clearing progress. / Confirm — cannot be undone." Names the verb, the effect, and the irreversibility in three short lines. This is the template the rest of the app should be held to.
- `registry-keys.png` — "Monetizer calls have nothing to reach." / "Monetizer runs will refuse." Concrete, specific consequences instead of a generic "not configured."
- `library-light.png` — the Clone conductor card volunteers its own discrepancy with the spec ("Differs from the original 8-node design by one node, fit_adjudicator, observed in live runs…") rather than silently matching the mockup. Exactly the honesty the brief asks for.
- `learning-evaluate.png` — "The gate is honest — this node needs prompt work (or its rubric recalibrated), and the next trial will show against exactly these cases." Explains a failing state and says what to do about it, unprompted.
- Toast pattern (`PromptTab.tsx:116`, `HistoryTab.tsx:104`, etc.) — "Prompt saved / `workspace_update_node_prompt` → recorded in History" is a good template: past tense, names the verb, names the consequence.

### Jargon / terminology check

- Internal verb names (`workflow_reset_run`, `playbook_curate`, etc.) are shown throughout confirm dialogs and toasts. Given the audience is a single engineer-operator who explicitly designed the system around "every control maps one-to-one onto a verb" (`proposal.html`), this is a deliberate and appropriate feature here, not jargon — flagging it only so it isn't "fixed" by a future pass that doesn't know the audience.
- No cross-screen synonym drift was found for the concepts that matter most (run status vocabulary — `queued/running/paused/blocked/completed/failed/cancelled` — is identical everywhere it appears; "live" vs "pinned" is used consistently as the editability vocabulary). The one real inconsistency is the gate-label imprecision documented above (every gate called a "publish decision").

### Housekeeping flag (not a copy defect, but worth a look before ship)

`edit-prompt.png` / `history-diff.png`: the Full Draft Writer's stored prompt and its History diff both contain the literal string "Appended for nodeedit.spec.ts: tightened schema-adherence clause." This reads like a Playwright test's own edit leaking into fixture content shown to reviewers as if it were real prompt text. Worth confirming this is test-run residue and not something that would ship — if it's fixture data generated by `nodeedit.spec.ts` running against a shared store, regenerate the fixture rather than leaving a test filename inside content an operator would read as their own prompt.

## Prioritised action list (merged, impact-per-effort order)

**Blockers** — these keep the console from meeting the "instantly legible, doesn't need explaining" bar and should be fixed before calling this WP-R gate passed:

1. **[Blocker]** Reserve amber for attention/gate states only; give ordinary primary actions (Save, Start run, Promote, Sign in, etc.) a neutral style. One CSS token (`base.css:52`) plus a sweep of `variant="pri"` call sites that aren't actually gate-adjacent. *(§7.8 fail — Part 1, highest-impact #1)*
2. **[Blocker]** Fix the gate-copy imprecision: stop calling every gate "the operator publish decision"; source the phrase per gate the way `gateApproveEffect()` already does internally. Add the same specificity to the Decline button label. *(§7.3 partial, gate-panel scrutiny — rewrite table rows 6–7)*
3. **[Blocker]** Remove the "mock backend" hardcoding from toast copy in `Observations.tsx` and `Optimizer.tsx` so the strings don't assert a false thing once the app is pointed at the live endpoint. *(Truth-telling — rewrite table rows 9–10)*

**High impact, low effort** — do next:

4. Consolidate the duplicated Gate explanation (center tab + dock) into one, keeping the dock's fuller version. *(Part 1, highest-impact #2)*
5. Rename the "Live" tab (or split running/paused visually from blocked within it) so the label matches its contents. *(Part 1, highest-impact #2; rewrite table row 1)*
6. Strip the design-rationale footers (Runs Live, Runs Grid, Registry Projects) down to operator-relevant content only; keep the "live vs. pinned" disclosures but give them distinct styling from these general footnotes so they read as load-bearing, not throwaway. *(Part 1, highest-impact #3; rewrite table rows 2–5)*
7. Fix the rail's fan-in glyph legibility (or swap for text) and add tooltips to the fan-in and "P" risk badges. *(Rewrite table rows 11–12)*
8. Fix the one present-progressive toast ("Retrying node" → "Retry requested") and the doubled JSON error message. *(Rewrite table rows 8, 14)*

**Polish** — lower priority, do when convenient:

9. Fill out the placeholder tool-registry descriptions ("Run artifact operation." ×4) with real one-line summaries.
10. Add a scroll affordance (fade edge or visible scrollbar) to the Graph overlay so cut-off DAG columns read as scrollable, not clipped.
11. Fix the toast/"fixture data" badge overlap in the bottom-right corner (`learning-compare.png`, `registry-tools.png`).
12. Confirm and, if real, regenerate the fixture content containing "Appended for nodeedit.spec.ts…" so no test-authoring residue is visible in reviewer-facing prompt/diff content.
13. Revisit the large unused whitespace on sparse screens (`runs-history.png`, `learning-evaluate.png`, `bench-build.png`'s empty right column) — least urgent, since a dense expert tool tolerating some breathing room on thin fixture data is a reasonable trade, but worth a look once real data volume grows.
