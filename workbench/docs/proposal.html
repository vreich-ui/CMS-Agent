CMS Agent Workspace · UI redesign proposal

From constellation to workbench

A single-operator console for building, testing, and improving agent workflows — where the run is the unit of work, node attributes are the center of the screen, and the graph is a map rather than a menu.

Prepared for Wolf Date 24 Aug 2026 Grounded in live workspace v630 · 3 conductors · 6 projects · 15 runs · 10 observations · 5 rubrics · 6 replay datasets

How I understand the task

What the UI must become, restated — and checked against the live system.

You are the only user of this surface. It is not an editor's tool and not a client's tool — it is the operator's workbench for a fleet of function-based agent workflows. Today that fleet is already real: I inspected the live workspace and found three conductors — publishing_conductor (23 nodes, the DTC publishing specialist), clone_conductor (8 nodes, site cloning & template generation), and capture_conductor (11 nodes) — with a foundation-charity publishing workflow planned. Clients are projects (dr-lurie, zilberman, fernwell, monetizer…) and a run binds a workflow to a project at start time. The current UI inverts this: the constellation graph sits at the center acting as a node picker, node attributes are peripheral, and client selection is entangled with workflow selection.

The redesign therefore has five jobs:

  • Put node substance at the center. Prompt, tools, skills, schemas, model config, dependencies — inspectable and editable as the main content of the screen, not a side drawer.
  • Make runs first-class. See what's running now, start runs (dry or live, mock or model), pause / resume / cancel / retry / run-until, and open any historical run in the workbench for analysis.
  • Reorganize node presentation around execution order, not spatial constellation position — with nodes that a given run never engaged greyed out or hidden.
  • Decouple client from workflow. Workflows are function-based; the client is a parameter of a run and a filter for analysis, never a mode the whole UI lives in.
  • Tidy the rest: auth & key management in one deliberate place, legacy pieces removed, everything reachable fast for a single expert operator.

Two findings from the live data sharpened the design more than anything else:

Finding one — your runs mostly stop at gates, so triage is the primary screen. Of the last 15 runs, seven are blocked (at theme_bind, publication_controller, publish_executor, capture_emit_live), three failed (at layout_analyst, reader_simulation, article_body), one cancelled, four completed. The most valuable pixel in this UI is not a node picker — it is the answer to "where did this run stop, why, and what do I do about it?" The design treats the blocked-at-a-gate state as a first-class object with its own panel, not as an error.

Finding two — the system already distinguishes live-editable attributes from seed-pinned topology. Run metadata states it plainly: prompt, schemas, tools, skills and model config are overlaid from the workspace store (your edits apply to the next run immediately), while topology — edges, risk levels, new nodes — is pinned to canonical definitions and needs a re-seed (nodes:update) plus redeploy. A UI that pretends everything is equally editable will lie to you. The node editor below marks every field as live or pinned, and pinned fields explain what a change actually requires.

Design principles

Six commitments that every screen decision below follows from.

The run is the unit of work

Building, testing and analyzing all happen in one room — the workbench — in two modes: Build (no run bound, you edit definitions) and Run (a run is bound, nodes wear its statuses). Same layout, same muscle memory.

The graph is a map, not a menu

The constellation survives as an optional overlay for structural understanding. Primary navigation is an ordered node rail grouped by pipeline phase — the "common order pattern" you described.

Client is a parameter

You pick a project when you start a run, and you filter by project when you analyze. Nothing else in the UI is client-scoped. Workflow selection lists functions, never clients.

Tell the truth about editability

Live-editable fields save to the store and apply on the next run. Pinned fields (dependencies, risk level, topology) are shown read-only with the exact re-seed step a change requires.

Gates and risk are visible form

Approval gates, risk levels (read / write / publish) and tool side-effects are encoded in shape and color everywhere they appear — a publish-risk node never looks like a read-risk node.

Single-operator density

No onboarding chrome, no role management. Dense tables, keyboard-first, a command palette (⌘K) that jumps to any node, run, workflow, project or setting by name.

The node rail

Topologically ordered, grouped by phase — for the publishing conductor: Intake → Strategy → Research → Planning → Drafting → Review → Build → Publish → Learning, derived from the node kind field the store already carries. In Run mode each node wears the run's status dot; nodes the run never engaged are dimmed (with a toggle to hide them outright), so a finished or in-flight run reads as a clean strip of what actually happened. Fan-in is annotated inline (e.g. brief_architect shows "⇐ 7 inputs") rather than drawn — the full graph is one keystroke away as an overlay, which is where the constellation's genuinely good representation earns its keep without owning the screen.

The center: editor and inspector, one surface

Selecting a node fills the center with tabs. In Build mode the first tab is Prompt; in Run mode the first tab is This run — the node's execution record for the bound run: validated input, effective prompt as resolved (node_get_effective_prompt), tool calls with results, duration, cost, retries, output with schema validation, produced artifacts. The remaining tabs are identical in both modes:

  • Prompt — the stored prompt with a diff against the shipped canonical text (the store already reports promptState: diverged), live-editable.
  • Tools — allowed tools with risk and side-effect badges pulled from the tool registry; add/remove is live-editable; approval-requiring tools visibly flagged.
  • Skills — assigned skills with effective resolution (skill_resolve_for_node) and links into the skills library.
  • Schemas — input/output JSON Schema editors with validate-before-save (workspace_validate_node).
  • Model & limits — budget USD, max turns, tool-call limit, timeout, retry count, max output tokens.
  • Dependencies — pinned: shown read-only with the note "topology changes require re-seed (nodes:update) + redeploy".
  • History — the change feed for this node (changes_list / changes_compare / changes_restore): every edit, diffable and restorable. This is your improvement-adjustment loop's safety net.
  • Learning — what the workspace has learned about this node and what it is doing with it: injected playbook lessons with provenance, observations that mention the node, its rubric and score trend, live optimizer proposals, and its fine-tune readiness. The per-node window into the loop described in the learning section below.

The run dock

The right-hand dock exists only when a run is bound (or being started). Every control maps one-to-one onto a verb the backend already exposes — no new server work: start dry run, run all, run next node, run until a chosen node, pause, resume, cancel, reset, retry node. Beside the controls: live cost against budget, node progress, the error list, and — critically — the gate panel. When a run is blocked, the gate panel names the gate, shows the readiness evidence (workflow_publish_readiness), and offers the operator decision (workflow_set_operator_publish_decision) inline. Blocked stops being a dead status and becomes a work queue of one.

The edit-and-retry loop

The whole point of the workbench is the tight loop LangGraph Studio proved out: run → inspect the node that disappointed → edit its prompt/tools/schema → retry that node in place → compare. The inspector's "This run" tab links directly to the editor tabs, and the dock's Retry node re-executes with your edits (the store overlay guarantees they apply). The History tab means every experiment is reversible.

The Runs surface

Monitor, history, and cross-run analysis.

Three tabs. Live: currently running and paused runs as cards — workflow, project, current node, progress, cost, and the stall flag your list API already computes (a "running" run whose driver died shows as stalled, with a nudge to reset or resume). History: the full table — run id, workflow, project, mode (dry/live · mock/model), status, started, duration, cost, error count — filterable by workflow, project, status, date, mode. Any row opens that run in the workbench. Grid: pick one workflow; recent runs become columns, nodes become rows, each cell a status chip. Ten runs of the publishing conductor side by side make "reader_simulation started failing on Thursday" visible in a way no single-run view can.

Starting a run

The launchpad — where the client enters the picture, and nowhere before.

Start run (from the library, the workbench, or ⌘K) opens a modal: workflow (preselected), project (the client binding — with connection health shown inline so you never launch against an unconfigured endpoint), execution mode (mock for free pipeline-shape tests, openai for live model output), dry run vs live, budget USD, request id, and the brief/input — validated against the entry node's input schema before the button enables. One modal, every knob, no hidden defaults.

The learning loop, made visible

The workspace already learns. The UI's job is to show it, steer it, and feed it.

I inspected the improvement subsystem, and it is more complete than the first draft of this proposal assumed. The backend already implements a full flywheel: observations (ten recorded — operational truths like "publish ≠ release, batch publishes and release once", the media-reference flip that was a build-breaker, the two-grammar mapping for Dr. Lurie, plus run diagnostics from learning_recorder and post-mortem lessons like the create_missing_object_id fix); ACE playbooks — curated, budgeted lessons per node, rendered into a prompt injection; evaluation rubrics (five active, weighted criteria, e.g. contract_intelligence scored on contract fidelity ×3, no-invented-rules ×2); frozen replay datasets (six); regression gates with baselines and verdicts (contract_intelligence currently held at 0.484 mean against a 0.85 threshold); an optimizer that proposes variants, runs trials against replays, promotes winners, and recommends a cost-aware model ladder; feedback records (approve / reject / edit / outcome, including monetizer revenue ingest); and a fine-tune readiness report (thresholds: 500 approved examples, 200 preference pairs).

The finding that shapes everything here: the flywheel is complete on the backend and empty at every human stage. Ten observations, but zero curated into playbooks. Rubrics exist, but the model ladder says "no model-attributed eval results yet." Zero feedback records, 0/200 preference pairs, 0/500 approved examples. That is not a backend gap — it is a capture-surface gap. So the learning UI has two halves: visibility (how is it learning, what has it changed) and capture (make your judgment cheap to record, because your judgment is the fuel).

How learning actually changes the workflow — three paths, all inspectable

Your "I'd like to see how it affects the workflow" has a precise answer in this system, and the UI shows each path where it lands:

  • Playbook injection → effective prompt. Curated lessons are rendered into the node's prompt at run time. The node editor's Prompt tab already shows stored-vs-effective; the Learning tab shows exactly which lessons are injected, at what budget, with provenance back to the observation each came from.
  • Optimizer promotion → node definition change. A promoted prompt variant or model-config change lands in the store, so it appears in the node's History tab as a diffable, restorable change — attributed to the trial that earned it, with its score delta.
  • Model ladder → cost/quality recommendation. Once eval results carry model attribution, the ladder recommends cheaper models where quality holds; shown in Model & limits with the evidence, applied with one click, reversible like any change.

The Learning surface

A fifth top-level surface, opening on the flywheel: the loop drawn as stages with live counts — observe → curate → evaluate → propose → trial → promote → regression-gate → dataset → tune — each stage clickable, each empty stage saying plainly what feeds it. Subtabs:

  • Observations — the feed, filterable by node and run, with one-click curate into playbook (playbook_curate / playbook_migrate_observations) and archive. Curation is a judgment call; the UI makes it a ten-second one.
  • Playbooks — per node: the curated lessons, their token budget, the rendered injection ("this is what the node actually receives"), and delta history.
  • Compare — your split-screen suggestion, specified below.
  • Evaluate — rubric editor (weighted criteria, versioned, restorable), results, and the regression watchboard: score sparkline per node, baseline markers, held/regressed verdicts flagged like failing CI.
  • Optimizer — per node: proposals with prompt diffs, trials scored against frozen replays, promote / auto-promote gates, model-ladder recommendation.
  • Datasets — frozen replays, SFT and preference exports, and the fine-tune readiness meters (0/500 · 0/200 today — the meters themselves are the motivation to use the capture surfaces).

Capture interfaces — Compare, and four more worth having

Split-screen Compare (your suggestion, and the right one to build first). Two candidates side by side — draft text, hero image, template, payload — same brief, pick A / B / tie / both bad, keyboard-first (1 / 2 / 0 / x), optional blind mode that hides which side is the current champion so the judgment is unbiased. Every verdict writes a feedback record and a preference pair, counting visibly toward the 200-pair fine-tune threshold. This is the Chatbot-Arena / RLHF pairwise pattern, and it is the highest-signal-per-second interface a single expert operator can have. Sources of pairs: optimizer trials (champion vs challenger on the same replay case), learning-mode candidate sets, or any two run outputs you select from history.

  • Annotation queue (LangSmith's pattern): recent node outputs, one at a time, against the node's rubric — approve / reject / edit-and-approve. Edits become SFT examples; the 500-example meter fills as a by-product of QA you'd want to do anyway.
  • Counterfactual replay: from any node inspector — edit the prompt, replay against the frozen dataset (optimizer_run_trial), and see old vs new outputs side by side with the score delta before promoting. The edit-and-retry loop, but against six known cases instead of one live run.
  • Champion / challenger shadow: a proposed variant rides along on real runs without affecting them; its outputs queue into Compare. Promotion happens only after your verdicts and the regression gate agree.
  • Outcome join: feedback_ingest_monetizer ties revenue and engagement back to the runs and nodes that produced the piece — the only feedback signal that arrives without costing you a click, shown on the flywheel and in run analysis.

Legacy removal

Explicitly retired in this design: the constellation as home screen and node picker (demoted to overlay); client selection as a global mode / workflow-selection dimension; any editor-facing chrome that leaked into the operator surface (the admin-chat path for editors remains its own surface, untouched); duplicate or dead panels that grew around the constellation. The command palette replaces most of the navigation the constellation was doing.

Architecture & migration

Design now, move hosting later — the two don't conflict.

Everything above is a thin client over the MCP/HTTP surface the workspace already exposes; I deliberately mapped every UI capability onto existing verbs, and found no screen that needs new backend work to reach usefulness. That has a pleasant consequence for the Netlify → Google Cloud question: the UI should be a static SPA (or a small Cloud Run service) talking to the same endpoints, so moving it is a redeploy, not a redesign. My suggestion: build the new workbench as a fresh front end against the existing API from day one, host it wherever is fastest today, and fold it into the g-cloud project when consolidation becomes the priority. Nothing in this proposal creates Netlify coupling.

  1. Workbench, read-only + RunsNode rail, inspector with "This run", run history and live strip, open-run-from-history. Highest analysis value, zero write risk. This alone replaces the constellation's daily job.
  2. Run control + gatesStart-run modal, pause/resume/cancel/reset/retry/run-until, the gate panel with operator decisions. The UI becomes the place runs are driven from.
  3. Node editing + historyAll editor tabs with live/pinned truth-telling, validate-before-save, change history with diff and restore. The improvement loop closes.
  4. Registry + legacy removalProjects, keys, tools, skills, agents, usage; retire the old surfaces; grid view; command palette polish.
  5. Learning surfacesFlywheel overview, observations → playbook curation, Compare (A/B) with preference capture, annotation queue, evaluate + regression watchboard, optimizer trials and promotion. Ordered last only because it builds on the workbench and runs surfaces — the capture interfaces are small once those exist.

Open questions

  • Foundation-charity conductor: when its node set firms up, does it share the publishing phases or need its own grouping vocabulary? The rail's phase grouping is data-driven (kind), so it should absorb it — worth confirming.
  • Approvals beyond publish: tool-level needs_approval policies exist per project — should those surface in the same gate panel, or stay a registry concern until one actually fires mid-run?
  • Blind-mode default in Compare: should champion identity be hidden by default (less bias) or shown (faster context)? I'd start blind with a reveal-after-verdict.
  • Constellation metrics: the attention/metrics endpoints suggest the constellation was also doing health visualization. If so, that job moves to the library cards and the grid view — confirm nothing else depended on it.

Companion piece: the interactive mockup — the workbench, runs surface, library and registry as a clickable dark-console prototype populated with your real node and run data. Pattern sources: n8n debug-and-re-run, n8n data pinning, n8n partial executions, LangGraph Studio.
